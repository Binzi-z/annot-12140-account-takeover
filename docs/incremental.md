# 增量扫描设计（incscan）

## 为什么上次漏了

旧增量按"文件哈希没变就跳过"做缓存：退款接口的改动落在调用方，被污染的
`db.Query` 在被调函数里，被调函数所在文件的缓存条目没有失效，增量直接复用了
旧结论。根因是**缓存粒度与依赖方向不匹配**：findings 不仅取决于本文件内容，
还取决于它调用的所有函数的摘要。

## 缓存模型

`.scancache/index.json`，以包为单位组织，每个条目都携带输入哈希：

- `files[rel]`：文件内容哈希 + 该文件的 findings
- `functions[pkg/Name]`：函数体哈希 + **摘要** + 它调用的函数列表（调用图边）
- `interfaces[pkg]` / `type_methods[pkg]`：接口方法集、类型的方法集（跨包实现判定用）

函数摘要是失效传播的最小单位：

- `return`：返回值携带哪些污点类别、来自哪个形参（如 `forward00` → 原样透传）
- `param_sinks`：哪个形参会流到哪个类别的 sink、在哪一行（如 `store.Lookup`
  的 `id` 流到第 8 行的 `db.Query`）——上月事故的模式，sink 在被调函数里时
  靠它在调用方触发结论

## 失效规则（影响面按导入图 + 调用图计算）

1. **源文件变更**（哈希不同/新增/删除）→ 重扫自己。
2. **被调函数变更**（摘要有差异，或函数被删除）→ 沿调用图反向边重扫**所有
   调用方**所在文件；调用方摘要若因此变化，继续向上传播到不动点。跨包时
   调用边本来就是按 import 解析的，影响面自然被限制在导入图可达范围内。
3. **跨包接口实现变更**（接口方法集增删改）→ 用结构匹配（类型方法集 ⊇ 接口
   方法集）找出新旧实现类的并集，重扫它们所在文件。
4. 只改注释/格式：函数体哈希变 → 重扫自己，但**摘要不变 → 不波及调用方**
   （回测 L 组验证）。

全量扫描 = 空缓存的增量扫描，同一条代码路径，因此"增量结论与全量逐条一致"
是构造性保证的，另有 50 样本回测逐条比对（冷、热两轮都比）。

## 回测与门槛

`python analyzer/backtest.py`：50 条标注样本（无实质变更、调用方增删净化、
被调函数变更、净化器本体破坏、新增文件、跨包 sink、接口/实现变更、事故复现
i1/i2、组合变更、sink 封装本体变更、仅注释变更）。每个样本断言：
冷增量==全量、热增量==全量、热增量==标注真值。门槛：召回 ≥ 85%、误报 ≤ 15%、
一致性 0 失配。当前结果：召回 100%、误报 0%、50/50 一致。

## SARIF 与 CI 拦截

```
python analyzer/scan.py inc --repo . --sarif findings.sarif
python analyzer/scan.py ci  --repo . --baseline main.sarif --sarif pr.sarif
```

`ci` 模式把当前结论与基线 SARIF 做 (file, line, ruleId) 集合差，**只拦截新增
违规**：有新增则逐条打印 `NEW VIOLATION` 并 exit 1，存量技术债不阻塞。

## 两个进程同时扫同一仓库：缓存一致性

设计原则：**缓存只是性能提示，不是事实来源**。任何条目被采用前都重新校验
输入哈希，校验不过就当缓存缺失重算——所以并发永远不会产生错误结论，最坏
只是重复计算。在此之上三层机制：

1. **内容寻址**：条目 key 是（文件哈希 / 函数体哈希），同一输入必然算出
   同一条目。两个进程同时算同一文件，写出的字节完全相同，谁后写都一样。
2. **原子写**：先写 `index.json.tmp.<pid>` 再 `os.replace` 同目录替换。
   读者只能看到完整的旧版或完整的新版，永远读不到半拉文件。
   （Windows 特有：读者打开文件的瞬间会阻塞 `os.replace` 抛
   `PermissionError`，这是平台文件锁语义而非逻辑竞争，写侧退避重试即可，
   race_test 的 T1 在 Windows 上复现过这个崩溃。）
3. **互斥锁合并**：读-改-写合并段持 `.scancache/lock`（`O_CREAT|O_EXCL`，
   锁内记录 PID+主机+时间戳，mtime 超过 120s 视为持有者已死可破锁）。
   合并是对磁盘缓存取并集——因为条目内容寻址，合并没有冲突可解，
   丢条目只损失性能。分析计算本身在锁外并行，锁只包住合并与落盘。

## 怎么测出这种竞争（`python analyzer/race_test.py`）

真进程并发（不是线程，GIL 会掩盖交错），并用 `INCSCAN_SLEEP_AFTER_LOCK`
环境变量在持锁后注入 sleep，把毫秒级的临界区拉宽到必然交错：

- **T1**：8 进程同时冷启动扫同一仓库（抢建缓存），所有输出必须逐条等于
  全量扫描，缓存必须是合法 JSON、无残留 tmp/lock 文件。
- **T2**：4 轮"变更代码 → 4 进程并发热扫描"，每轮每个进程的结论都必须
  等于当轮全量——验证并发下失效传播不丢。
- **T3**：测试进程先占锁，扫描进程短超时必须报错退出（rc=3），解锁后必须
  成功——证明互斥真的生效，不是摆设。
- **T4**：伪造 mtime 超阈值的 stale 锁，扫描必须破锁并正常完成——证明
  进程崩溃不会把仓库锁死。
- **T5**：持锁后 sleep 0.5s 强制两进程交错，结论仍须一致、缓存完好。
